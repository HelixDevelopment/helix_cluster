# pkg/build — Anti-Bluff Audit

- **Test result:** PASS — 17 tests in `pkg/build` + 16 tests in `pkg/build/cache` = 33 tests, all PASS (`go test ./pkg/build/... -count=1`).

- **Risk:** HIGH

- **Real-behavior coverage:**
  - **Genuinely proven (cache + platform + manifest):** The `cache`, `platform`, and `manifest` units are honest. `cache_test.go` verifies sink-side behavior: `TestMemoryCachePutGet`/`TestDiskCachePutGet` compare retrieved bytes against input via `bytes.Equal`; three explicitly-named `_Mutation` tests (lines 164-200) prove copy-on-Put, copy-on-Get, and on-disk persistence across a fresh `DiskCache` instance — each would FAIL if the behavior were removed. `TestDiskCacheCreatesPrefixDir` (line 143) checks the real filesystem layout. `platform_test.go` has a real parse table with error cases, casing/whitespace normalization, and a round-trip test. `manifest_test.go` proves Add/Get/Remove/Platforms sorting and empty-digest rejection.
  - **NOT proven (the build orchestration itself):** The `Service`/`Job` build pipeline — the package's headline feature ("build orchestration primitives") — is exercised only against a hard-coded simulation, not a real build. `runBuild` (build.go:242-262) does not clone a repo, read a Dockerfile, or invoke any builder; it `time.After(100ms)`, then branches on the magic string `j.RepoURL == "fail"` and synthesizes `j.ImageTag = "helix/<id>:<ref>"`. The code even comments "Override in production" (line 241), confirming the tested path is a stub. Per CLAUDE-1, a test asserting `state == succeeded` and `ImageTag != ""` on this stub is a PASS-bluff: it proves the simulator ran, not that any image was built.

- **PASS-bluff findings:**
  - **build_test.go:64-92 `TestServiceSubmitAndGet` — PASS-bluff on non-functional feature.** Asserts `got.State == StateSucceeded`, `got.ImageTag != ""`, `len(GetLogs()) != 0`. All three are satisfied by the simulation in `runBuild`: success is unconditional for any RepoURL other than the literal `"fail"`, `ImageTag` is a formatted string never derived from a real build, and logs are static strings. No image, layer, digest, or registry artifact is ever verified to exist. This is exactly the §7.1 PASS-bluff the constitution names — "a test that passes on a non-functional feature."
  - **build_test.go:128-147 `TestServiceFailedBuild` — tautological failure injection.** The only way to reach `StateFailed` is `RepoURL == "fail"` (build.go:253). The test sets `RepoURL: "fail"` and asserts `StateFailed`. It proves the hard-coded string compare, not real build-failure handling (bad Dockerfile, missing ref, compiler error, OOM). No real failure path is covered.
  - **build_test.go:149-158 `TestServiceList` — uses a Service that was never Start()ed.** `NewService(1)` then `Submit` x3 with no `svc.Start(ctx)`. Workers never run, so jobs sit `StateQueued` forever; the test only counts map size (`len == 3`). It asserts nothing about processing and would pass even if `runBuild` were deleted.
  - **build_test.go:94-103 `TestServiceSubmitDuplicate` — same: no Start(), only the duplicate-ID guard is exercised.** Fine as a unit check but contributes to the illusion of coverage without exercising the worker pipeline.
  - **build_test.go:160-185 `TestServiceConcurrentSubmits` — asserts only `len(jobs) == 10`, swallows every `Submit` error.** `svc.Submit(j)` return value is discarded inside the goroutine (line 172). With queue cap 100 and 10 jobs it won't overflow, but the test cannot detect a Submit failure and never verifies the 10 builds reached a terminal/succeeded state. Happy-path map-count only.
  - **build.go state machine — no mutation-paired test for `IsTerminal`/auto-timestamps via the Service path, and timing-based tests use `time.Sleep(300ms)`.** `TestServiceSubmitAndGet`/`TestServiceFailedBuild` depend on a 100ms simulated build finishing inside a 300ms sleep — flaky-by-construction and tied to the stub's timing, not real work.
  - **No sink-side evidence for the build feature** as required by CLAUDE-1 rule 6: no captured image, no registry push, no Docker/buildkit invocation, no end-user-visible artifact. The feature claims "build orchestration" but is never run against a real builder, violating CLAUDE-1 rules 1 (real integration/e2e), 3 (sink-side), and 5 (no mock-only validation for real-world features).
  - **Minor (cache):** `Digest` is never used to validate stored content — `DiskCache.Put`/`MemoryCache.Put` accept any `digest` string for any `data` (content-addressable storage is claimed in the package doc, line 1, but integrity is unenforced). No test asserts that a corrupted/mismatched digest is rejected on Get; an end user could store data under a wrong digest and no test would catch it.

- **Recommended hardening:**
  1. **Make the build path real or quarantine the claim.** Either (a) inject a `Builder` interface into `Service` and add an integration test that runs a real builder (e.g., `docker buildx`/buildkit) against a fixture repo+Dockerfile, then asserts the produced image exists and is pullable (sink-side evidence per CLAUDE-1.6); or (b) if `runBuild` is intentionally a simulator, rename it and the tests to `*_Simulated`, add a `t.Skip`-with-reason guard for the real path, and stop asserting success implies a built image.
  2. **TestServiceFailedBuild:** drive a genuine failure (invalid Dockerfile / unreachable repo / builder non-zero exit) and assert the error surfaces in `Job.Logs` and `State == StateFailed` — not the `"fail"` sentinel.
  3. **TestServiceList / Concurrent:** call `svc.Start(ctx)`, wait for terminal states, and assert each job reached `StateSucceeded`; check `Submit` return values instead of discarding them. Add a queue-overflow test that fills the 100-slot queue and asserts `"build queue is full"`.
  4. **Replace `time.Sleep` polling** with synchronization (completion channel or `Job.Done()`), and add a mutation test that fails if `TransitionTo` validation or `IsTerminal` is removed (e.g., assert `queued->succeeded` is rejected, terminal re-transition is rejected, and `StartedAt`/`CompletedAt` timestamps are set by the Service worker, not just by direct `TransitionTo`).
  5. **Cache integrity:** add a test asserting `Get` either rejects or is documented not to verify `Digest(data) == digest`; if content-addressability is a real guarantee, enforce it in `Put`/`Get` and test the mismatch rejection.
  6. **Cancel mid-flight:** add a test that cancels a job while `runBuild` is in-flight and asserts the context-cancellation branch (build.go:246-249) sets `StateCancelled` and logs "cancelled" — currently uncovered.
