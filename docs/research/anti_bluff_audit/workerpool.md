# pkg/workerpool — Anti-Bluff Audit

- **Test result:** PASS (4 tests: TestPool, TestPool_MultipleWorkers_Mutation, TestPool_StopWaitsForWorkers_Mutation, TestPool_NilWorkSafe_Mutation)
- **Risk:** MEDIUM
- **Real-behavior coverage:** The tests exercise the REAL `Pool` implementation (no mocks/stubs) and prove several genuine, end-user-visible behaviors:
  - `TestPool` proves a submitted closure is actually executed by a real goroutine worker (sink-side: `counter` is incremented and observed via atomic load, guarded by a 2s timeout against deadlock).
  - `TestPool_MultipleWorkers_Mutation` is a genuine mutation-paired test: it uses a barrier to force all 3 tasks to run simultaneously and asserts `maxActive == 3`. If `New(n)` were mutated to spawn only 1 worker, tasks would serialize, `maxActive` would be 1, and the test would FAIL. This proves the `n`-parallelism contract for real.
  - `TestPool_StopWaitsForWorkers_Mutation` proves `Stop()` blocks until in-flight work finishes. Because `Submit` is an unbuffered-channel send (`p.work <- fn`), the send only returns once a worker has received the task, so by the time `Stop()` runs the worker is mid-execution; `wg.Wait()` then blocks until the 50ms sleep completes and `completed` is set. This is real sink-side verification and would fail if `wg.Wait()` were removed.

- **PASS-bluff findings:**
  - **package_test.go:76-86 (`TestPool_NilWorkSafe_Mutation`) — weak / near-tautological.** The test has NO assertion. Its entire correctness claim is "reaching here without panic means nil guard is in place" (comment, line 85). A panic inside the worker goroutine does NOT fail the test deterministically — `panic` in a non-test goroutine crashes the whole test process, but only if the scheduler runs the worker before `Stop()`; the `time.Sleep(50ms)` makes that likely but not guaranteed, and there is no sink-side proof the nil work item was even consumed. This is a happy-path-only smell: it neither asserts an effect nor reliably proves the guard. Mutation-pairing is asserted in the comment but not enforced by code.
  - **package.go:41-43 (`Submit`) — failure path entirely unproven.** `Submit` blocks forever on `p.work <- fn` if the pool is already stopped (all workers have exited via `stopCh`), causing a goroutine leak / hang. No test submits after `Stop()`, so this real, end-user-reachable hang is uncovered. There is also no panic-recovery in `worker()` (package.go:26-38): if a submitted `fn` panics, it kills `wg.Done`'s defer path only for that worker and crashes the process — no test covers a panicking task, so resilience claims are unproven.
  - **Submit return value / backpressure semantics unverified.** `Submit` returns nothing and provides no "accepted" signal; tests rely on side effects only. There is no test that work submitted concurrently from multiple goroutines is all eventually executed (no count-N fan-in assertion), so the "pool" throughput contract is only proven for a single task in `TestPool`.
  - **No test that `Stop()` is idempotent / safe to double-call.** `close(p.stopCh)` will panic on a second `Stop()`. Real end users calling `Stop()` twice get a crash; uncovered.

- **Recommended hardening:**
  1. Give `TestPool_NilWorkSafe_Mutation` a real sink: have the nil submission be followed by a non-nil submission that signals a channel, and assert the worker survived and processed the subsequent task (proves the nil was skipped, not just "no panic"). Without this, mutation removing the `if fn != nil` guard is not reliably caught.
  2. Add a fan-in test: submit N tasks from the caller, each incrementing an atomic counter and signaling a `sync.WaitGroup`; assert the final counter == N after `Stop()`. This proves no task is dropped — the core pool guarantee.
  3. Add a panicking-task test (requires adding `recover()` in `worker()` first, then asserting the pool keeps processing later tasks). Currently a panicking task is a latent process-crash with zero coverage.
  4. Add a post-Stop `Submit` test (e.g., run `Submit` in a goroutine with a timeout) to document/guard the hang, and add idempotent `Stop()` (guard the `close`) with a test calling `Stop()` twice.
  5. Strengthen `TestPool_StopWaitsForWorkers_Mutation` by also asserting that NO further task submitted after the in-flight one runs, and by checking elapsed time >= 50ms to prove the wait was real rather than coincidental scheduling.
