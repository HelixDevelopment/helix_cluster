# pkg/wasm — Anti-Bluff Audit

- **Test result:** PASS — 8/8 tests pass (`go test ./pkg/wasm/... -count=1 -v`): TestHostLoadModule, TestHostInstantiateAndCall, TestHostCallMissingFunction, TestHostCallBeforeInstantiate, TestHostLoadMissingFile, TestWasmPluginLifecycle, TestWasmPluginExecuteBeforeInit, TestWasmPluginDoubleShutdown.

- **Risk:** MEDIUM

- **Real-behavior coverage:** The `Host` layer is genuinely exercised against the REAL Wasmtime runtime (`bytecodealliance/wasmtime-go/v29`), not a mock. Tests embed real WASM bytecode (`simpleAddWasm` built from WAT), write it to a temp file, compile it via `wasmtime.NewModuleFromFile`, instantiate with WASI linking, and invoke the exported `add` function. `TestHostInstantiateAndCall` performs strong sink-side verification: it asserts `add(10,32) == 42`, which is a real computed result returned from the WASM VM and would fail if compile/instantiate/call were broken — this is a proper mutation-paired assertion for the core call path. Failure paths are covered: missing function (`ErrFunctionNotFound`), call-before-instantiate (`ErrNotInstantiated`), and missing file all assert `err != nil`. This is honest, end-to-end proof that the Host can load and run real WASM.

- **PASS-bluff findings:**
  - `plugin.go:55-64` + `plugin_test.go:32-34` — **PASS-bluff in the headline plugin feature.** `WasmPlugin.Execute` calls `host.Call(execFn, len(input))` but **discards the WASM return value** (`_, err := ...`) and then `return input, nil` — it echoes the caller's own input back. The test `TestWasmPluginLifecycle` asserts `string(out) == "hello"`, i.e. it asserts the literal it just passed in (`p.Execute([]byte("hello"))`). This proves nothing about what the WASM module produced; the assertion would still pass even if the WASM `execute` function returned garbage, returned a different value, or did nothing observable. The plugin's own source comment admits this: "The real implementation would use WASM memory; here we pass the length as a simple integration signal." So the advertised "execute a plugin and get its output" feature is not actually wired to WASM output, and the test masks that gap. This is a tautological-assertion + no-sink-side-verification bluff per CLAUDE-1.
  - `plugin.go:48` and `plugin.go:71` — `Init` swallows the result/error of the `init` export (`_, _ = h.Call(p.initFn)`) and `Shutdown` swallows the `shutdown` export result (`_, _ = h.Call(p.shutdown)`). No test verifies that `init`/`shutdown` exports were actually invoked or had any effect. `TestWasmPluginLifecycle` would pass identically against a module that exported none of init/execute/shutdown (since errors are ignored). There is no mutation-paired test that would fail if the init/shutdown calls were removed entirely.
  - `TestWasmPluginExecuteBeforeInit` (`plugin_test.go:40-46`) — passes `/dev/null` as the path but never calls `Init`, so it only exercises the `p.host == nil` guard. It does NOT prove the failure path through a real load failure of an invalid module; the `/dev/null` path is never actually loaded. Weak (happy-guard only), though not strictly a bluff.
  - `TestWasmPluginDoubleShutdown` (`plugin_test.go:48-60`) — only asserts `err == nil` twice (idempotency). It verifies no panic / nil-return, but does not verify the underlying store/engine were actually released (no sink-side check that `host.Close()` ran or that resources are freed). Trivial-assertion smell, acceptable as a regression guard but not proof of cleanup.

- **Recommended hardening:**
  1. Make `WasmPlugin.Execute` honest: have it actually use the WASM return value (or WASM linear memory) to produce output, then write a test using a WASM module whose `execute` transforms the input (e.g. returns `len*2` or writes a known byte pattern to memory) and assert the **transformed** result — not the echoed input. Today's test must be changed so it would FAIL if `Execute` ignored the WASM call.
  2. Add a negative test where the module is missing the `execute` export and confirm `Execute` surfaces `ErrFunctionNotFound` (currently `init`/`shutdown`/`execute` absence is silently tolerated).
  3. Add an `Init` failure test that loads a structurally invalid `.wasm` (corrupt bytes) and asserts `Init` returns a wrapped error — proving the load/instantiate error path, not just the `host == nil` guard.
  4. Assert that `init` and `shutdown` exports actually run: use a WASM module that records a side effect (e.g. writes a sentinel value to exported memory) and verify after `Init`/`Shutdown` that the sentinel changed, so removing the `h.Call(initFn)`/`h.Call(shutdown)` lines would fail a test (mutation pairing per Constitution 1.1).
  5. In `Host.Call`, add a test covering the `ErrUnexpectedResult` branch (a function returning a non-i64 / multi-value result) — currently uncovered.
