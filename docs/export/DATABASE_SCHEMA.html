DATABASE_SCHEMA

Helix Cluster OS — Database Schema Reference

PostgreSQL 16+ is the authoritative relational store for the Helix Cluster control plane: the node registry, GPU inventory, sessions and their window/pane tree, resource reservations, the scheduling queue, health snapshots, LLM advisories, the build subsystem, users, the migration-history ledger, network policy, cluster config, and an append-only audit log.

This document is generated by reading the real SQL under migrations/postgresql/. Every table, column, constraint, index, trigger, and function below is grounded in those files. Where two sources disagree, that divergence is called out explicitly rather than papered over.

1. Two schema sources — read this first

There are two distinct, independently-applied schema definitions in migrations/postgresql/, and they are not byte-identical. Understanding which one your environment runs is essential before trusting any column/constraint detail.

1a. The golang-migrate chain (001–015, what make migrate-up applies)

The numbered pairs 001_*.up.sql … 015_*.up.sql (with matching *.down.sql) are the golang-migrate migration chain. This is the set applied by make migrate-up:

  • Makefile target migrate-up runs bash scripts/run-migrations.sh up (Makefile:78-80).
  • scripts/run-migrations.sh invokes the migrate binary against migrations/postgresql/ (scripts/run-migrations.sh:59-67).
  • golang-migrate only recognizes files matching {version}_{title}.{up|down}.sql. The numbered pairs match; 0001_primary_schema.sql does not (it has no .up.sql/.down.sql suffix), so the migrate runner ignores it.

This chain creates 14 tables (no CHECK constraints, fewer indexes, and some different table names — see §1c) plus the trigger/function set in migration 015.

1b. 0001_primary_schema.sql (the consolidated “authoritative” schema)

0001_primary_schema.sql is a single consolidated file (header: “Authoritative Postgres 16+ Primary Schema — 15 tables, CHECK constraints, ~53 indexes, triggers, audit”). It is not part of the golang-migrate chain (see §1a). Instead it is applied directly by Go code:

  • internal/schema/schema.go SchemaPath() resolves migrations/postgresql/0001_primary_schema.sql (internal/schema/schema.go:108).
  • ApplyPrimarySchema() streams the file to psql -f - over stdin, for both local-DSN and podman exec (container) transports (internal/schema/schema.go:279-308).

This file defines 15 tables with full CHECK constraints, GIN indexes, helix_- prefixed triggers/functions, an audit_log DEFAULT partition, partitions through 2027-06, and seed rows for cluster_config.

Honesty note (CLAUDE-1/CLAUDE-3): the project ships both a migrate chain and a consolidated schema, and they differ. The full distributed/production application path (which source is canonical in a deployed cluster, and reconciliation between the two) is not validated end-to-end here — this reference documents what each SQL file declares, not a single unified deployed database. Treat 0001_primary_schema.sql as the richer, constraint-complete definition and the 001–015 chain as the migrate-driven baseline.

3. How migrations are applied

# Apply all pending migrations (the 001..015 chain)
make migrate-up                      # → scripts/run-migrations.sh up

# Roll back exactly one migration
make migrate-down                    # → scripts/run-migrations.sh down 1

Details (Makefile:76-84, scripts/run-migrations.sh):

  • DATABASE_URL defaults to postgres://helix:helix@localhost:5432/helix_cluster?sslmode=disable (Makefile:76); override it for non-local targets. The script can also assemble the DSN from DB_HOST/DB_PORT/DB_NAME/DB_USER/DB_PASS/DB_SSLMODE (scripts/run-migrations.sh:13-35).
  • The script requires the golang-migrate migrate binary on PATH or at ~/go/bin/migrate; otherwise it errors with install instructions (scripts/run-migrations.sh:20-30).
  • Additional sub-commands: up [N], down [N], version, force V, create NAME, validate (up → down 15 → up), status (scripts/run-migrations.sh:37-123).

The consolidated 0001_primary_schema.sql is applied separately by the Go helper internal/schema.ApplyPrimarySchema, which pipes the file to psql -f - (works for both local DSN and podman exec container transports) (internal/schema/schema.go:279-308).

4. Trigger functions

Defined in 0001_primary_schema.sql:7-56 (and the equivalent un-prefixed versions in 015_triggers_and_functions.up.sql:7-61).

helix_update_updated_at_column() / update_updated_at_column()

BEFORE UPDATE row trigger. Sets NEW.updated_at = NOW() and returns NEW. Attached to every table carrying an updated_at column.

helix_audit_trigger() / audit_trigger()

AFTER INSERT OR UPDATE OR DELETE row trigger, SECURITY DEFINER (per code comment, so it can always INSERT into audit_log). It inserts a row into audit_log with: - event_type = <TG_OP>_<TG_TABLE_NAME> (e.g. INSERT_nodes) - severity = WARNING for DELETE, else INFO - actor = current_setting('app.current_user', TRUE) or 'system' - resource_type = table name, resource_id = row id::TEXT - action = the operation, details = to_jsonb(OLD|NEW)
