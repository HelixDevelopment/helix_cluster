Why this matrix exists (the sink-side gate)

Per CLAUDE-1 (§7.1 + §11.4.39), tests are necessary but not sufficient. A green test on a non-functional feature is a PASS-bluff — the same defect class as a §7.1 violation. Phase 8C (the Chutes-AI remote-GPU integration) may not be declared usable by an end user on the strength of unit tests alone. This document is the sink-side gate: each Phase 8C exit gate (a CLAUDE-1 usability criterion drawn from roadmap §8) is mapped to the end-user-visible behavior it proves, the evidence type that proof requires, the current status, and a pointer to a real test or the Queued ticket that will close it.

Honesty rule (this IS the deliverable): a row is marked PROVEN only when a real, existing test/evidence file exercises the behavior on the host OS. Where only unit-level or record-layer proof exists (and the roadmap demands a live worker / real hardware / a higher-level flow), the row is PARTIAL. Where the implementation or its test is absent — even if the registry marks the ticket “Completed” — the row is NOT-YET and cites the Queued (or missing) ticket. The registry Completed flag is not accepted as evidence; only resolvable test files are.

Status legend: PROVEN = real test/evidence exists and runs on host · PARTIAL = real proof exists for a subset; roadmap-level gate (live worker / hardware / higher flow) not yet met · NOT-YET = no resolvable test/impl; tracked by a Queued ticket.

Grounding correction (supersedes a prior PASS-bluff guard): an earlier revision asserted G17 (HXC-1607) and G18 (HXC-1608) had no implementing code/test in the tree. That was a grounding error: it searched only pkg/marketplace for Bounty/Payout/Meter/Register and never consulted the registry item_history.evidence_path, which names the real implementation locations — pkg/metering for HXC-1607 and pkg/auditproof for HXC-1608, both landed in the same commit 9ad74be cited for the Completed marks. The flows DO exist and their closure-level behavior is proven (TestClosure1_RegisterClaimMeterPayout, TestClause2_TamperDetected, both passing on host). They are therefore PARTIAL (closure-level PROVEN; UUID-tagged live captured-evidence run still open), not NOT-YET. The registry Completed flag is still not by itself accepted as sink-side evidence — the upgrade to PARTIAL is justified by the resolvable, passing test files, not by the flag. The genuine residual concern is mutation coverage: the registry records a single FAILED mutation bite per gate (drop-units-term → TestClosure1; Verify-always-true → TestClause2), which is real but does not equate to code-nonexistence.

Bottom line: Phase 8C’s trust/confidentiality primitives are genuinely proven at the unit/record layer on the host, and the marketplace economic + audit flows now have proven closure-level implementations (G17/G18 PARTIAL). Phase 8C is still NOT yet declarable end-user-usable (G22 NOT-YET): the live-worker, real-hardware, throughput, and the UUID-tagged captured-evidence economic/audit runs remain open and tracked by Queued tickets.
